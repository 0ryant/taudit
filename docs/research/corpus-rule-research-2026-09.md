# taudit — corpus robustness and rule-research pass

Report date: 2026-09-08. Binary under test: taudit 1.3.3, **debug build**, `C:/Users/0ryant/.cargo/shared-target/debug/taudit.exe`, on Windows 11 Pro 26200 (win32) only.

---

## 1. Robustness verdict

**taudit survived the corpus with zero stability defects: no panics, no bad exit codes, no invalid JSON, no non-deterministic exploit graphs, no timeouts, across 79,304 invocations over 4,141 files.** There is no bug list in this section because there are no bugs to list.

What that claim covers, so it can be audited:

| Platform | Files | Invocations | Panics | Bad exits | Invalid JSON | Non-determ. | Timeouts | Parse failures |
|---|---|---|---|---|---|---|---|---|
| GitHub Actions | 1,093 | 30,617 | 0 | 0 | 0 | 0 | 0 | 5 |
| Azure DevOps | 1,000 | 15,170 | 0 | 0 | 0 | 0 | 0 | 10 |
| GitLab CI | 1,034 | 16,301 | 0 | 0 | 0 | 0 | 0 | 1 |
| Bitbucket | 1,014 | 17,216 | 0 | 0 | 0 | 0 | 0 | 11 |
| **Total** | **4,141** | **79,304** | **0** | **0** | **0** | **0** | **0** | **27** |

Every file received at minimum the mandated matrix: 7 commands, with the exploit-graph command run twice for a byte-comparison determinism check (8 invocations/file). Every slice reported full coverage with no sampling and no truncation, and slice membership was mechanically defined (`ls <dir>/*.yml | sort | awk 'NR % 3 == k'`), so the slices are disjoint and exhaustive. All runs used per-worker scratch CWDs so that `.taudit/receipts` and `audit-trail.jsonl` writes could not contend; no `.taudit/` was written into the corpus or the repo.

Two caveats on the coverage claim, both material:

- **Invocation depth was uneven.** Five of twelve slices ran exactly the mandated 8 invocations per file; the rest ran 14–32 per file with slice-local extra sweeps. So "every output format on every file" is true at the mandated-matrix level; the deeper sweeps are not uniform across the corpus and their results are not comparable slice-to-slice.
- **File arithmetic is off by one.** The slice totals sum to 4,141; the brief states 4,142. I cannot reconcile this from the data provided. Per-platform corpus denominators also disagree between agents (Azure quoted as both 1,000 and 1,001; GHA as 1,093 total but 1,086 or 1,088 parseable; GitLab 1,034 / 1,033 / 1,021; Bitbucket 1,014 / 1,003 / 1,002). Treat every denominator in this report as ±1%.

**Parse failures (27 files, 0.65%) are counted separately and are not automatically defects.** The public corpus contains templated files (Jinja/Handlebars placeholders that are not valid YAML), truncated captures, and files whose declared platform does not match their content. A scanner that refuses such a file is behaving correctly. However: **none of the 27 were individually triaged in this pass.** Any one of them could be a genuine parser defect masquerading as bad input. That triage is a small, bounded piece of work and it is not done.

Two things the zero-defect result does *not* establish:

1. **Determinism was tested back-to-back, same process environment, same host.** It does not cover cross-host, cross-OS, locale-sensitive, or across-process-restart hash-iteration-order determinism.
2. **Concurrent audit-trail behaviour is untested by construction.** Every harness deliberately isolated worker CWDs specifically so concurrent `.taudit/audit-trail.jsonl` appends could not contend. That is good harness hygiene and it means concurrent-append correctness has zero coverage from this pass.

## 2. New rule candidates, ranked

Ranking is by severity × incidence × precision, with a discount applied to any candidate whose incidence figure I cannot reconcile.

**Read this before the table.** In 7 of 26 survivors the harness match count disagrees with the proposing agent's own prose count — in one case severely (`fetched_artifact_executed_without_verification` reports `matches 0` alongside a 13-file body claim). Both numbers are shown below where they differ. **No incidence figure in this report should reach release notes without a single deterministic re-measurement script run against a frozen corpus snapshot.** Separately, every precision claim ("11/11 true positives", "zero false positives observed") is the *proposing* agent's self-review. The skeptics re-ran fixtures and read source; they did not re-adjudicate matched corpus files. Treat precision claims as hypotheses.

**1. Credential passed as a command-line argument** — *four platforms: GHA, Azure DevOps, GitLab, Bitbucket*

Merged from `gha_secret_in_process_argv`, `ado_credential_in_process_argv`, `gitlab_durable_secret_on_process_command_line`, `credential_passed_as_command_line_argument`.

A step hands a long-lived credential to a CLI as an argv value (`docker login -p $PASS`, `dotnet nuget push --api-key $(Key)`, `twine upload -p "$TWINE_PASSWORD"`, `vsce publish -p $VSCE_TOKEN`) instead of via stdin or env. The cleartext lands in `/proc/<pid>/cmdline` for the process lifetime, readable by every other process in the job — service sidecars, lifecycle scripts from `npm install`, co-tenants on a shell-executor or self-hosted runner — and by anything that echoes its own invocation under `set -x` or on error.

| | |
|---|---|
| Incidence | GHA 7/1,086 (0.64%) · ADO 11/1,001 (1.10%) · GitLab 66/1,033 (6.5%) · Bitbucket 44/1,014 (4.34%). Union ≈128 files ≈3.1% of corpus. Harness match counts disagree: 2 / 8 / 60 / 46. |
| Closest existing | `short_lived_sas_in_command_line` — correct threat model, its own text cites `/proc/*/cmdline` — but hard-gated on an Azure SAS mint (`New-AzStorage*SASToken`) plus ADO task-field sinks. Measured 0 hits on the entire Azure corpus and 0 on GitLab. `gha_helper_path_sensitive_argv` is a PATH-shadowing rule despite the name. |
| Why it misses | The argv *position* of a credential is unmodelled anywhere in the rule set. `COMMAND_LINE_SINK_TOKENS` (rules.rs ~2065) holds only ARM/Az keywords and is reachable only behind the SAS/VM-remote-exec preconditions. No credential-passing flag vocabulary exists. |
| Discriminator | Credential flag (`-p`/`--password`/`-k`/`--api-key`/`--token`/`-u user:$VAR`/`-Dkey=`) immediately followed by a secret reference, AND the name is credential-shaped, AND it is not an ephemeral platform token, AND the line carries no `--password-stdin`/`--token-stdin`/`<<<`/`--*-file` form. |
| FP risk | **Moderate, and the exclusions are load-bearing rather than cosmetic.** On GitLab the ephemeral-token exclusion (`CI_JOB_TOKEN`, `CI_REGISTRY_PASSWORD`, …) is the difference between 66 files (6.5%) and 144 files (14.1%) — at 14% the rule describes normal GitLab CI rather than a defect. On ADO the credential-name test plus stdin exclusion takes 26 files down to 11 and removes 15 genuine safe cases (`mkdir -p $(dir)`, `docker run -p $(port):80`, `-p $(Build.ArtifactStagingDirectory)`). Ship it wrong and it is noise. |
| Severity | **Medium**, not high. This is co-tenant observability of a credential, not publication of one. Escalate to high on self-hosted/shared pools, where the observer is a different tenant rather than the same job. The ADO proposer argued high; I disagree on the base case. |

Highest incidence in the set, only cross-platform pattern with a single shared discriminator, and the only candidate where one core helper serves four platform registrations.

**2. Bitbucket self-hosted-runner blindness** — *Bitbucket*

Merged from `bitbucket_self_hosted_runner_untrusted_trigger` (critical) and `bitbucket_shell_runner_host_execution` (high). Both are gated behind the same parser defect.

A `pull-requests:` step declares `runs-on: [self.hosted, ...]`. Bitbucket clones the PR source branch implicitly — there is no opt-out checkout step — and runs the script on operator-owned, long-lived infrastructure with a reused working directory. Any contributor who can open a PR gets code execution on that machine; `npm ci` alone runs attacker-authored lifecycle scripts, and the implant survives into the next run of the *deploy* pipeline that shares the box. The second shape is the reserved runner-type labels (`linux.shell`, `windows.powershell`, `macos`), which execute directly on the host OS with no container at all and silently ignore `image:`.

| | |
|---|---|
| Incidence | 11/1,014 (1.1%) self-hosted, of which 6 are PR-reachable (0.6%); 4/1,014 (0.4%) shell-runner types. |
| Closest existing | `self_hosted_pool_pr_hijack` and `shared_self_hosted_pool_no_isolation`. |
| Why it misses | **A confirmed parser bug with a measured blast radius.** `crates/taudit-parse-bitbucket/src/lib.rs:792` `step_looks_self_hosted` calls `map.get("runs-on").and_then(|v| v.as_str())`. Real Bitbucket YAML writes `runs-on` as a *sequence* (at least two labels are mandatory), so `as_str()` returns `None` and `META_SELF_HOSTED` is never set. Measured: **0 of 3,830 nodes across all 1,003 parsed Bitbucket reports carry self-hosted metadata**, and `attacker_surface_kinds` never contains `self_hosted_runner`. A scalar fixture does set the flag, isolating the sequence form as the break. `options.runs-on` (pipeline-wide default) is not read at all. |
| Discriminator | Effective `runs-on` label set contains `self.hosted` (case-insensitive) and the step is reachable from `pull-requests` or `default`. Separately: label set contains a no-container runner type. Do not fire on Atlassian-hosted steps (999/1,014 files). |
| FP risk | **Low** for the label match itself, which is unambiguous. The risk is elsewhere: `META_SELF_HOSTED` is currently consumed as a *suppressor* in `unpinned_action`, `action_major_version_pin_without_sha` and `pr_trigger_with_floating_action_ref`. Fixing the parser will start suppressing findings on ~15 Bitbucket files that currently report them. That is a behaviour change requiring a baseline diff, not a pure addition. |
| Severity | Critical for the PR-reachable case. Persistent RCE on operator infrastructure, reachable by anyone who can open a PR. |

This is the highest-severity item in the report and the cause is a one-expression parser defect, not a judgment call.

**3. Remote fetch-then-execute — three matcher-shape gaps in one predicate** — *Azure DevOps, GitLab, Bitbucket (GHA presumed, unmeasured)*

Merged from `remote_payload_fetched_to_file_then_executed`, `fetched_artifact_executed_without_verification`, `remote_script_piped_to_shell_via_wrapper`, `remote_script_piped_to_language_interpreter`, `downloaded_artifact_executed_without_integrity_verification`.

A pipeline fetches code from a mutable remote endpoint and runs it, in a spelling the matcher does not recognise. Whoever controls that endpoint executes arbitrary code on the runner in a job that later holds publish credentials. There is a specific irony worth putting in front of the maintainer: taudit's own remediation string for `runtime_script_fetched_from_floating_url` advises "fetch to a file, inspect, then run" — following taudit's advice converts a high finding into total silence without removing any risk.

Three sub-shapes, all rooted in `body_has_pipe_to_shell_with_floating_url` (`crates/taudit-core/src/rules.rs:3343`), a fixed-substring list:

| Sub-shape | Example | Measured |
|---|---|---|
| (i) Interpreter token set too narrow | `curl https://getcomposer.org/installer \| php`, `\| python3 -`, `\| node -` | 10 GitLab files (1.0%) |
| (ii) Wrapper between pipe and interpreter | `\| sudo bash`, `\| DAGGER_VERSION=$(V) sh` | 7 Azure files |
| (iii) Fetch to file, execute later (no pipe) | `curl -o tool; chmod +x tool; ./tool` | 9 Bitbucket, 13 Azure (7 mutable + 6 pinned), 2 Azure fetch-exec subset |

| | |
|---|---|
| Union incidence | Roughly 40–45 files across three platforms. **The sub-populations overlap and nobody measured the union.** The helper lives in `taudit-core` and is platform-agnostic, so GHA is almost certainly affected too — that is a hypothesis, not a measurement. |
| Why it misses | Shapes (i) and (ii) fail on the substring list; the URL-mutability half (`line_url_is_mutable` / `url_is_pinned`) is already correct and would fire if reached. Shape (iii) has no filename-binding concept at all — the rule never correlates a download target with a later execution of that basename. |
| Discriminator | (i) and (ii): replace the substring list with a regex on the pipe segment allowing optional `VAR=`/`sudo`/`env`/`nohup` prefixes and a widened interpreter set, requiring the interpreter to be the first token after the pipe. Every other gate unchanged. (iii): correlate a fetch with an explicit output flag against a later same-basename execution or `chmod +x` within one job. |
| FP risk | **Low for (i) and (ii)** — 0 of 990 Azure files match the widened form on a non-fetch line; precision is inherited unchanged from the existing mutability gate. **Moderate for (iii)** — requires both the explicit output flag and a basename match to hold at 0.20% on Azure; dropping the mutability gate raises it to 5/990 and the extra 3 are all correctly-pinned release assets. |
| Note | Five of five skeptic dissents in this cluster said the same thing: real gap, but it is a predicate widening, not a new rule. They are right about (i) and (ii). Shape (iii) is arguable — filename binding is new machinery, even if it lives inside an existing rule ID. |

**4. Integrity verification is entirely unmodelled** — *GitLab measured, applies everywhere*

`integrity_check_disabled_on_dependency_fetch` (0/3 refuted) plus the negative-discriminator half of the Bitbucket/Azure fetch-exec candidates.

The pipeline explicitly switches off the transport or signature check protecting an external fetch, then builds or ships what it downloaded: `wget --no-check-certificate` pulling a toolchain installer that becomes the build environment; `GIT_SSL_NO_VERIFY: "true"` alongside `GIT_SUBMODULE_STRATEGY: recursive`, so every third-party submodule source arrives over an unauthenticated channel and is compiled into the artifact; `yum install -y --nogpgcheck`. No account compromise is required — anyone who can MITM the runner's egress substitutes the payload, and the pipeline has deleted the only control that would notice.

| | |
|---|---|
| Incidence | 7/1,034 GitLab (0.68%) with guards; 12 without, of which 5 are mischaracterised. Separately, **zero of 1,001 Azure pipelines verify any checksum or signature anywhere** (no `sha256sum`, `Get-FileHash` comparison, `gpg --verify`, `cosign verify`), and exactly 1 of 1,002 Bitbucket files does. |
| Why it misses | Repo-wide grep for `no-check-certificate`, `gpgcheck`, `GIT_SSL_NO_VERIFY`, `trusted-host`, `allow-untrusted` across `crates/`, `docs/`, `schemas/`: **zero hits**. The word `checksum` appears 5 times in `rules.rs`, all inside `Recommendation::Manual` strings — advice the tool gives, never a condition it tests. A digest-pinned image plus `wget --no-check-certificate` of the actual toolchain scores clean today. |
| Discriminator | The verification-disabling token must sit on a line that also performs an external fetch or install, with three measured guards: `--allow-unauthenticated` must co-occur with `apt`; rpm gpg bypass must not target a local path (a project installing its own just-built RPMs is legitimate); `curl -k` must carry an output flag and not `-X POST`/`--data`. |
| FP risk | **Low.** Guards were derived from named real false positives in this corpus (`gcloud run deploy --allow-unauthenticated` is a Cloud Run IAM flag; `zypper --no-gpg-checks build/.../*.rpm` installs the project's own output). One residual class — `curl -k -X POST` of a token to an API — is real but belongs to the secrets lens, not supply chain. |

Cheapest genuinely-new detection in the set: a token match with three guards, no dataflow required. Note that "verification explicitly disabled" and "verification simply absent" are different populations; only the former is cheap.

**5. Secret materialised into a durable credential file or store** — *GHA + GitLab measured; ADO rule exists but is syntactically ADO-only*

Merged from `gha_secret_to_persistent_credential_store` (0/3) and `gitlab_secret_materialised_to_disk_credential_file` (1/3). Two sub-shapes with the same finding class: a secret stops being step-scoped env and becomes a file on disk that outlives the writing command.

GHA shape: a `run:` step hands `secrets.*` to a tool whose *documented behaviour* is to write that credential in cleartext into a long-lived store under `$HOME` (`composer config --global github-oauth.github.com`, `poetry config pypi-token.pypi`, `gh auth login --with-token`, `dotnet nuget add source`, `aws configure set`). Every subsequent process in the job reads it with zero env access, and in all four corpus instances the very next steps execute third-party lockfile code. On self-hosted runners `$HOME` persists across jobs and repositories, so the credential outlives the run entirely. GitLab shape: `echo/printf "$KEY" > path` into either the workspace (artifact- and cache-reachable, next-job-readable) or a `$HOME` credential store.

| | |
|---|---|
| Incidence | GHA 4 files. GitLab 29/1,021 (2.8%), harness count 22. |
| Closest existing | `secret_materialised_to_workspace_file`. |
| Why it misses | Structurally dead outside ADO for three independent reasons. (1) `rules.rs:2627` builds its needle as `format!("$({secret})")` — ADO macro syntax; `${{ secrets.X }}` and `$VAR` never match. (2) `line_references_workspace_path` (rules.rs:2593) knows only `$(System.DefaultWorkingDirectory)`, `$(Build.SourcesDirectory)` etc. — no `$CI_PROJECT_DIR`, no `~/.ssh`, no `$HOME`. (3) The GHA hits write through a *tool* rather than a shell redirect, so `line_writes_to_file()` misses independently. Fired on 0 of 1,033 GitLab files. |
| Discriminator | GHA: value resolves to `secrets.*` (inline or env-bound) AND the command is on a closed allowlist of credential-store writers. **Explicitly exclude `docker login`** — measured, including it adds exactly one corpus file and that file uses the safe `--password-stdin` form. GitLab: emitter form (segment starts `echo`/`printf`/`cat`/`base64`/`jq` and the secret precedes the `>`), credential-shaped name minus a benign set, not an ephemeral platform token, target not `/dev/*`/`/tmp/*`/`/kaniko/*`, no stdin consumer on the line. |
| FP risk | **Low-moderate.** The emitter-form condition alone removed every curl-header false positive (`curl -H "PRIVATE-TOKEN: $TOK" > notes.md` is correctly silent). One residual FP acknowledged by the proposer (a cache content-hash named `CURRENT_KEY`), ≈3% on that sample. The GitLab corpus contains 69 files using the *safe* stdin form, which is a genuine in-corpus control proving the discriminator separates two populations. |
| Blocked on | The GitLab parser mints Secret nodes only for `variables:`/`secrets:` keys (`taudit-parse-gitlab/src/lib.rs:1018,1043`). A project-level CI/CD variable referenced only from `script:` — how nearly every real secret arrives — has no Secret node at all. |

**6. GHA `release` trigger is not treated as attacker-reachable** — *GitHub Actions*

Anyone holding `contents: write` calls `POST /repos/{o}/{r}/releases` with `target_commitish` set to any commit they control. GitHub creates the tag and fires `release`; `actions/checkout` with no `ref:` checks out that attacker-chosen commit, builds it, and publishes it with the org's long-lived credential. The `release` event accepts no `branches:`/`tags:` filter — only `types:` — so branch protection on main is *structurally* inapplicable, and without a deployment `environment:` there is no reviewer gate.

| | |
|---|---|
| Incidence | 34/1,086 files have a `release` trigger; 16 also have a publishing credential and a real publish sink; the environment/ref-gate clauses split them **13 vulnerable / 3 gated**. The 3 excluded all bind `environment: pypi` or `environment: CI/CD` — an in-corpus positive control. |
| Closest existing | `risky_trigger_with_authority`. `RISKY_TRIGGERS` (rules.rs:6553) is exactly `{issue_comment, pull_request_review, pull_request_review_comment, workflow_run}`; `release` is not a member, and the rule fires on 0/1,088 corpus files. |
| Why it misses | One missing string. The skeptic proved it decisively: a probe byte-identical except `release` → `workflow_run` fires `risky_trigger_with_authority` at **high** — the candidate's own proposed severity — with the `PYPI_API_TOKEN` Secret node already built and matched. |
| FP risk | **19% as-is, and that is the whole story.** Adding `release` to `RISKY_TRIGGERS` alone will fire on all 16, including the 3 that are correctly gated by `environment:`. The GHA parser never reads a job's `environment:` key — grep for `environment` in `crates/taudit-parse-gha/src/lib.rs` returns only env-var comments — so `META_ENVIRONMENT_NAME` is never populated on GHA and no rule can observe whether an approval gate exists. **This item is a one-word change coupled to a small parser field; ship them together or ship a 19%-FP rule.** |
| Classification | Gate correction, not a new rule. The skeptic who refuted it was right about classification and wrong to treat that as reducing its value. |

**7. ADO release gate decoupled from upstream success** — *Azure DevOps*

A stage/job/step carrying publish, deploy or code-signing authority runs regardless of whether the build/test/scan stage succeeded. Three ADO-specific mechanisms: writing a custom `condition:` on a stage **replaces** the implicit `succeeded()`; `dependsOn: []` explicitly severs previous-stage ordering so the release stage runs *in parallel with* the test stage; `condition: succeededOrFailed()` / `always()` on the publishing task itself. The test gate the author believes protects the release is decorative.

| | |
|---|---|
| Incidence | 4/1,001 (0.40%); harness count 9. |
| Closest existing | `security_job_silently_skipped` (GitLab-only, keys on `allow_failure: true` on scanner-*named* jobs) and `prod_deploy_job_no_environment_gate` (ADO, but keys only on a prod-named service connection and reads neither `condition:` nor `dependsOn:`). |
| Why it misses | The ADO parser already stamps the AND-joined condition chain as `META_CONDITION` (`taudit-parse-ado/src/lib.rs:1237-1270`) and three GHA rules consume it — **nothing on the azure-devops path does.** Nothing anywhere models `dependsOn`, and no rule knows the ADO semantic that a custom condition discards implicit `succeeded()`. Proven: fixtures `f5` (condition without `succeeded()`) and `f5b` (identical but `and(succeeded(), ...)`) produce byte-identical output. taudit cannot distinguish the vulnerable spelling from the correct one. |
| Discriminator | Unit carries publish/deploy/signing authority, is downstream of something, and shows one of: `dependsOn: []`, a non-empty `condition:` containing **no** status function at all, or a condition that is exactly `always()`/`succeededOrFailed()`. |
| FP risk | **Low, but entirely dependent on the authority clause.** 14 corpus files use `always()`/`succeededOrFailed()` and only 1 is on an authority step — the rest are `PublishTestResults`/log-upload steps, which is the overwhelmingly common and correct use. Drop the authority conjunct and this rule is unusable. |
| Blocked on | ADO parser stamping `dependsOn`. |

Unanimous survivor (0/3), genuinely novel logic, but low incidence — 0.40%.

**8. Mutable ref on an include, component or import** — *GitLab + Bitbucket*

Merged from `gitlab_component_mutable_version_ref`, `gitlab_include_ref_mutable_beyond_branch_allowlist`, `bitbucket_import_crossrepo_pipeline_mutable_ref`. Included or imported YAML redefines the consumer's jobs and runs with the consumer's `CI_JOB_TOKEN`, id tokens and project variables. Anyone with push access to the source branch silently rewrites every consumer's pipeline on the next run.

| | |
|---|---|
| Incidence | GitLab components 10/1,033 (0.97%); GitLab includes 6–7/1,033 (0.58%); Bitbucket imports 8/1,014 (0.79%), across 20 import statements, **all 20 branch-pinned, zero version pins**. |
| Closest existing | `unpinned_include_remote_or_branch_ref` (GitLab), `template_extends_unpinned_branch` (ADO-only, returns empty without `META_REPOSITORIES`). |
| Why it misses | GitLab: the matcher is allowlist-shaped rather than deny-unless-immutable. The `component:` arm fires **only when `git_ref` is empty** (rules.rs ~10018), so `@main`, `@master` and `@~latest` all produce a non-empty ref and fall straight through with no mutability test at all. The `project:` arm tests a six-name `MUTABLE_BRANCH_REFS` list, so `production`, `stable`, `staging` are treated as immutable by omission. `remote_url_uses_branch()` returns `None` unless the URL contains the literal `/-/raw/`, dropping `raw.githubusercontent.com` and GitLab's own legacy `/raw/<ref>/` form. This is the same defect class already fixed in `runtime_script_fetched_from_floating_url`; the fix was never applied here. Bitbucket: **the parser has no `import` handling anywhere** — an import-only context is a mapping, `process_step_sequence` expects a sequence, and the walk returns without calling `graph.mark_partial()`. All 8 corpus files produce `nodes=0, findings=[], completeness="complete"`. |
| Discriminator | Invert both GitLab tests to deny-unless-immutable (40-hex SHA, semver/tag shape, or `$CI_COMMIT_SHA`/`$CI_COMMIT_TAG`). Exclude the bare-major form `@3`/`@4` — 14 corpus files, all self-owned within `to-be-continuous`. Bitbucket: fire when a pipeline context value is a mapping containing `import:` and the middle segment is not an immutable pin. |
| FP risk | **Low.** Corpus refs that must stay silent do: `v2.93.0`, `3.4.0`, `v5.16`, a 40-hex SHA, `template_release@0.4.0`, `$CI_COMMIT_SHA`. The bare-major exclusion is the only judgment call. |

**The Bitbucket half contains the worst single fact in this report: taudit currently reports `completeness: "complete"` and a clean bill of health on 8 files whose entire execution body is someone else's mutable branch.** That misreporting should be fixed regardless of whether any rule ships — a structural completeness gap is the minimum acceptable output.

**9. Bitbucket models a deployment binding as a *mitigation*** — *Bitbucket*

Not a rule candidate; a soundness inversion surfaced independently by two agents while investigating `bitbucket_prod_deployment_in_default_pipeline` and `bitbucket_pr_pipeline_binds_deployment_environment`.

`is_protected_deployment_name()` returns true for any deployment name containing prod/stag/deploy, and `process_step` then sets `META_ENV_APPROVAL="true"`. `path_crosses_env_approval()` (rules.rs:248) **downgrades** `authority_propagation`. Verified by fixture pair: an identical PR step holding `$AWS_SECRET_ACCESS_KEY` reports `authority_propagation` at **high** without `deployment: Staging` and at **medium** with it. Bitbucket deployment environments have no YAML approval mechanism whatsoever — the only in-YAML gate is `trigger: manual`, and the parser reads no `trigger:` key at all. **Adding the construct that widens blast radius currently makes taudit quieter.**

Fix: never infer approval from a deployment-environment name on Bitbucket. This will raise severities on existing findings; needs a baseline diff.

Two things follow from this that matter more than any individual kill.

First, **the same axis explains 11 of the 26 *survivors*' single dissents.** Where a survivor was refuted 1/3, the dissenting skeptic almost always said "real gap, wrong classification" rather than "no gap". Several skeptics also built positive controls to prove their own harness was live before reporting silence — that is the right discipline and it is why the silences reported above can be trusted.

## 5. Residual risk

**What this pass did not cover.**

*Environment.* One OS (win32), one build profile (debug), one binary (1.3.3). Linux and macOS are untested, and they differ in exactly the places these rules reason about: `$HOME` semantics, path separators, `/proc` availability, process spawning. Debug asserts were live, which is the conservative direction for panic-hunting, but release-profile behaviour (integer wrapping rather than panicking) is untested. **A release-build pass on Linux is the single highest-value robustness gap remaining.**

*Determinism.* Two back-to-back runs, same process environment, same host, same build. This does not cover cross-host determinism, locale sensitivity, or hash-iteration ordering that differs across process restarts on a different seed. The exploit-graph determinism claim is narrower than it reads.

*Concurrency.* Every harness deliberately isolated worker CWDs so concurrent `.taudit/audit-trail.jsonl` appends could not contend. Concurrent audit-trail and receipt writing therefore has **zero coverage** from this pass and remains a live unknown.

*Corpus shape.* Public repos, one file per repo, skewed toward small projects. Enterprise pipelines — large ADO template libraries, GitLab includes fanning into 20-file graphs, GHA reusable-workflow chains — are underrepresented. taudit is a per-file scanner, so multi-file authority graphs were out of scope by construction; several candidates (item 8 especially) are about exactly the boundary where the per-file model stops being sound.

*Parse failures.* 27 files failed to parse and none were triaged individually. Any of them could be a real parser defect.

**What would change the conclusions.**

1. **A single deterministic re-measurement script.** Incidence figures disagree between the harness match count and the proposing agent's prose in 7 of 26 survivors, in one case catastrophically (`matches 0` vs a 13-file prose claim). Until one script measures all discriminators against one frozen corpus snapshot, every percentage in Section 2 is approximate to roughly ±30%, and the ranking could reorder — particularly between items 5, 6 and 8, which are separated by single-digit file counts.

2. **Independent true-positive adjudication.** Every precision claim ("11/11 true positives", "zero false positives observed", "all 22 manually inspected") is the *proposing* agent's own review of its own matches. The skeptics re-ran fixtures and read source; none re-reviewed a matched corpus file. If the real precision on the argv cluster is 70% rather than ~100%, item 1 drops below item 3, and the GitLab half at 6.5% of corpus becomes actively harmful.

3. **A findings-volume baseline.** Nothing in this pass measured what any proposed change does to *existing* output. Items 0.1 and 0.3 will both change current findings — 0.1 will *suppress* some, 0.3 will *raise* some. Without a before/after count on a frozen corpus, these are unshippable, and if the volume shift is large the Tier 0 sequencing needs to change.

4. **The union of the fetch-execute populations.** Item 3 merges five candidates whose corpus sets overlap by an unmeasured amount. If the overlap is large the cluster's true yield is closer to 25 files than 45, which moves it below item 4.

5. **Whether the argv cluster's severity is medium or high.** I have called it medium against one proposer's argument for high. If the maintainer's threat model weights shared/self-hosted pools heavily — and Bitbucket's runner situation (item 2) suggests it should — the severity rises and item 1's already-first ranking becomes uncontested.
