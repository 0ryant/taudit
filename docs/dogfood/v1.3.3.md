# Dogfood report — taudit 1.3.3

Maintainer self-attestation required by [`RELEASE_GATES.md` §2.2](../RELEASE_GATES.md).
taudit 1.3.3 was run against its own CI estate on all four supported platforms
and against four sibling projects' estates. Every number below is reproducible
with the commands given; nothing here is quoted from memory.

Binary: `taudit 1.3.3`, the published release build. Date: 2026-09-09.

## Why this report exists in this form

The gate asks whether the tool works on YAML the maintainer did not write. This
release cycle produced a sharper version of that question, because a large share
of the CI YAML in this repository is now written by an AI coding agent rather
than by hand. Two findings below are the direct result, and they are the reason
this report leads with case studies rather than with totals.

A count of findings proves the tool emits output. A finding that changed the
code proves it was worth running.

---

## Case study 1 — an agent-written pipeline, caught before merge

`azure-pipelines.release-assets.yml` was written from scratch during the 1.3.3
release cycle, by an agent, to build macOS and arm64 release assets while GitHub
Actions was unavailable. It was scanned before it was committed.

| | Findings | critical | high | medium | info |
|---|---|---|---|---|---|
| As written | 9 | 0 | 1 | 6 | 2 |
| As merged | 3 | 0 | 1 | 0 | 2 |

The six `parameter_interpolation_into_shell` findings were the point. The
pipeline took a free-form `version` parameter and template-expanded it directly
into six inline `bash` steps, in the shape:

```yaml
run: curl -sSfL -o taudit.crate "https://static.crates.io/crates/taudit/taudit-${{ parameters.version }}.crate"
```

Azure Pipelines expands `${{ }}` before the shell sees the script, so the
parameter is not a shell variable being quoted. It is raw text spliced into the
program. Anyone with **queue build** permission could have supplied a `version`
containing shell metacharacters and executed arbitrary commands on the agent, in
a pipeline that holds a release-signing path.

The fix was to hand the value to the step through `env:` and validate its shape
first, so the shell receives a variable rather than substituted text:

```yaml
env:
  TAUDIT_VERSION: $(TAUDIT_VERSION)
run: |
  case "$TAUDIT_VERSION" in
    [0-9]*.[0-9]*.[0-9]*) ;;
    *) echo "##vso[task.logissue type=error]version must be X.Y.Z"; exit 1 ;;
  esac
  curl -sSfL -o taudit.crate "https://static.crates.io/crates/taudit/taudit-${TAUDIT_VERSION}.crate"
```

Reproduce, against the merged file:

```bash
taudit scan azure-pipelines.release-assets.yml --platform azure-devops
```

## Case study 2 — an existing workflow hardened, with an honest caveat

Scanning `.github/workflows/` surfaced four critical findings in
`taudit-pr-diff.yml`, from two rules: `gha_script_injection_to_privileged_shell`
and `script_injection_via_untrusted_context`. Two steps interpolated pull-request
context straight into a privileged `run` block:

```yaml
run: |
  BASE=${{ github.event.pull_request.base.sha }}
  HEAD=${{ github.event.pull_request.head.sha }}
```

**These were not exploitable.** Both fields are 40-character commit SHAs
produced by GitHub. An attacker cannot place shell metacharacters in them. A
reader who stopped at the severity label would have over-read the risk, and this
report says so plainly.

They were still worth fixing, for two reasons. The safety argument depends on
knowing which context fields are attacker-controlled, and that list is a moving
target, so the guidance is to never interpolate into `run` at all. And the same
file already passed a different value through `env:` correctly, so the two lines
were an inconsistency rather than a considered decision.

| `.github/workflows/` | Findings | critical | high | medium | low |
|---|---|---|---|---|---|
| Before | 32 | 9 | 15 | 7 | 1 |
| After | 28 | 5 | 15 | 7 | 1 |

The four criticals that cleared are exactly the two rules above. The five that
remain are all `authority_propagation`, discussed under "not fixed" below.

## What was not fixed, and why

Reporting only the fixed findings would misrepresent the signal. These stayed.

- **Five critical `authority_propagation` on our own workflows.** These describe
  `GITHUB_TOKEN` reaching many sinks in a job. They are structural facts about
  the workflow rather than defects, and this repository already documents why
  they stay advisory in
  [`contributing/dogfood-taudit-verify.md`](../contributing/dogfood-taudit-verify.md).
  A CI estate that builds, tests, signs and publishes will have broad token
  reach by construction.
- **`over_privileged_identity` on every Azure Pipelines file.** The remedy is the
  organization's *Limit job authorization scope* setting, not anything editable
  in the YAML. taudit cannot see that setting, so it reports the worst case.
- **`template_extends_unpinned_branch` (2) in `azure-pipelines.stack-integration.yml`.**
  Accurate. The templates are pinned to a branch, not a commit. Pinning them is
  tracked work, not a 1.3.3 fix.
- **`unpinned_action` in `bitbucket-pipelines.yml`.** Accurate, and deliberate
  for now: the pipe in question has no immutable digest form we consume.
- **22 `info` findings on Azure Pipelines**, mostly `untrusted_with_authority`
  against the platform-injected `System.AccessToken`. Every task receives that
  token by design. The rule says so in its own message, and `info` is the
  correct severity for it.

## Signal-to-noise, stated plainly

Of 64 findings on our own estate, 10 changed code during this cycle: 6 from case
study 1, 4 from case study 2. The rest are either accurate descriptions of
accepted structure, or platform facts taudit cannot resolve from YAML alone.

That ratio is the honest one to quote. The two rules that produced every fixed
finding, `parameter_interpolation_into_shell` and the two script-injection
rules, are precisely the rules that model untrusted input reaching a privileged
shell. On this evidence those rules earn their keep, and the propagation rules
are better read as a map than as a defect list.

## Tooling note

`--platform gitlab-ci` is rejected; the accepted value is `gitlab`. The error
message suggested the correct value, so this cost one retry rather than a
misreading, but the four-platform documentation should use the accepted spelling
consistently.
